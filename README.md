# Production Release

`production-release` 是一个面向 Codex 的生产发布 Skill。它负责把仓库中已经准备好的改动，沿着仓库原生流程完成版本判断、发布准备、质量检查、PR 与 CI、合并、标签、制品发布和消费端验证。

```text
发布请求
  → 发现仓库发布规则
  → 解析版本、渠道和停止点
  → 更新版本与发布说明
  → 执行可信质量门禁
  → PR / CI / 合并
  → tag / registry / hosting release
  → 从真实消费端验证
```

## 与 git-ship 的区别

本项目参考了 [`oil-oil/git-ship`](https://github.com/oil-oil/git-ship) 在触发边界、执行预览、验证命令发现和失败说明方面的设计。两者解决的问题不同：

| | `git-ship` | `production-release` |
| --- | --- | --- |
| 主要目标 | 把工作区改动通过分支、PR 和 squash merge 送进 `main` | 完成跨 Git、托管平台和制品仓库的生产发布 |
| 范围 | GitHub Git 交付 | npm、PyPI、Cargo、容器、托管 Release 等 |
| 策略 | 固定、明确的 Git 工作流 | 优先遵循目标仓库已有发布策略和自动化 |
| 完成标准 | PR 已合并并回到最新 `main` | 制品已发布，并从真实消费者环境验证成功 |

因此，本项目吸收它的清晰度和安全提示，但不会固定使用 `main`、`origin`、`gh`、stash、squash merge 或 `git add -A`。

## 使用方式

将此目录放入 Codex 或其他兼容客户端能够发现的 Skill 目录，入口文件是 `SKILL.md`。

完整发布下一个版本：

```text
发布这个仓库的下一个生产版本。
```

只准备发布 PR，不继续合并或发布：

```text
准备下一个 patch 版本的 release PR，停在 draft PR。
```

恢复中断的发布：

```text
npm publish 刚才超时了。检查外部状态，安全地继续发布，不要重复上传。
```

明确说“发布、发版、publish、ship”时，Skill 会以完成发布为目标持续执行；只要求检查、准备或创建草稿时，它会停在指定阶段。

## 工作原则

- 先读取仓库说明、版本来源、CI 和发布自动化，再决定操作方式。
- 在第一次修改前展示已解析的版本、来源、渠道、检查项和停止点。
- 审查范围、暂存范围、打包范围和发布范围必须一致。
- 验证命令必须来自可信仓库证据；找不到时明确报告，不自行编造。
- 不绕过失败的必需检查、分支保护或强制人工审批。
- 不覆盖已有版本或标签；远端响应不明确时先查询状态，再决定是否重试。
- 上传成功不等于发布完成，必须从真实 registry 或消费环境再次验证。

## 项目结构

```text
production-release/
├── SKILL.md            # Agent 执行规范
├── agents/openai.yaml  # Codex 展示信息和默认提示
└── README.md           # 面向使用者和维护者的说明
```

## 维护

修改发布行为时，请保持改动聚焦，并同时说明成功路径、失败路径和恢复方式。不要为单一仓库硬编码分支名、合并策略、包管理器或托管平台；目标仓库的规则始终优先。

本仓库尚未选择开源许可证。在仓库所有者明确决定许可证之前，不应假定第三方拥有复制、修改或再发布权限。
